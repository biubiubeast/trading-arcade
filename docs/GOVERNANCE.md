# 版本、文档与进度管理

## 建议：每次发布留档，每次小改记变更

需要留存。发布档案用于回答“当时承诺了什么、实际验证了什么、下一步为什么改变”；代码提交负责回答“究竟改了哪些行”。二者结合才能回溯。普通开发动作不必重复生成整套文档，以免副本互相矛盾。

## 两层结构

- 当前事实：`docs/PRODUCT.md`、`docs/ROADMAP.md`、`docs/QA.md`、`docs/ARCHITECTURE.md`。日常迭代可更新，以当前可用版本为准。
- 冻结快照：`docs/releases/vX.Y.Z/{PRODUCT,ROADMAP,QA,SUMMARY}.md` 与 `VERSION.json`。冻结后不得原地改写；勘误放下一版 SUMMARY，并引用原条目。
- 导航：根 CHANGELOG 是发布索引；`docs/releases/README.md` 关联版本、差异、源码和发布结果。
- 决策：`docs/DECISIONS.md` 用短 ADR 记录关键取舍，避免只在聊天里保留原因。

## 一份版本总结应有的内容

目标与本次范围；承诺/交付/延期的对照；可追踪验收 ID 和证据；模型与数据兼容变化；已知缺口；下一版优先级与原因；代码引用、网站发布 URL。验收结果必须区别自动测试、浏览器实测、用户研究和未检查。

本项目 v0.1 档案由已经发布的旧文档重建，并注明来源；不得追认未执行的验收。v0.2 起在正式发布前冻结。

## 固定发布步骤

1. 开始迭代时，更新当前目标与验收 ID；更改承诺时记录原因。
2. 实现与适量测试；在 QA 中逐条记录结果和未覆盖部分。
3. 写当前版本 SUMMARY（放版本目录），更新 CHANGELOG 与版本索引。
4. `node scripts/releases.mjs archive 0.2.0`：复制当前三份文档并生成 SHA-256 清单。脚本拒绝覆盖已冻结版本。
5. `node scripts/check.mjs`：语法与档案校验；`node --test tests/*.test.js`：业务检查。
6. 提交代码，创建 `v0.2.0` 标签；推送同一源码并发布网站。源码 hash 保存在 VERSION.json，最终提交与部署 ID 记在外部发布收据，避免自引用循环。
7. 对新发现的问题建 issue，注明目标版本、验收 ID、优先级和完成条件；不要事后改旧版计划。

## 版本号与分支

0.2.1 用于修正，不改变主要学习机制；0.3.0 用于新增内容分享等能力。模型计价或评分变化另增加 rulesVersion；存储兼容变化另增加 schemaVersion，不能仅改页面显示版本。

默认 main 保持可用，开发使用 feature 分支，发布点用不可移动 tag。补档时保留 `archive/v0.1.0` 分支作为完整代码基线，后续不在该分支开发。新项目已在 GitHub 独立私有仓库管理，与黄金期权仓库分离。

## 轻量任务管理

近期采用 GitHub Issues：`feature / bug / research / docs` 分类，`P0 / P1 / P2` 优先级，每个 issue 关联目标版本和具体验收条件。Milestone 对应版本，关闭任务需要证据。等多人并行时再增加 Projects 看板，不必先引入复杂管理工具。

## 自动化的边界

已提供只读 CI 配置和档案校验，不把测试通过当作产品效果验证。远端 CI 是否执行、是否通过，应读取 GitHub 的真实结果；配置文件存在本身不代表通过。SHA 清单能检测误改，但不是密码学签署或防篡改保证。
