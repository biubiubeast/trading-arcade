# 后续开发建议与交付流程

## 迭代顺序

| 阶段 | 目标 | 具体交付 | 放行条件 |
|---|---|---|---|
| v0.1 当前 | 完整的静态学习闭环 | 六关、实验、估值、复盘、进度、文档 | 核心检查通过、参考解可解、关键浏览器操作通过 |
| v0.2 | 验证理解而非记忆 | 预测问答、无轮廓迁移题、成本变化、操作回放 | 学习者能解释成本与收益边界，并解出改参数题 |
| v0.3 | 形成内容系统 | 关卡 JSON schema、课程编辑、组合分享、导入校验 | 非开发者可编制可验证关卡，分享内容安全可复现 |
| v0.4 | 第二个可玩游戏 | 波动率捕手、种子行情、对冲账本、三个基准 | 账本守恒、费用只扣一次、同种子可完全重放 |
| 后续 | 专业训练体系 | QuoteCraft / Alpha 侦探局、能力地图、团队课程 | 先完成小范围用户验证，再投入账号与分析后台 |

以上为建议次序，不承诺日期。每阶段均可单独发布，避免一次引入多款未完成游戏。

## v0.2 优先事项

1. 在关键动作之前让玩家预测：卖出 Call 后成本和尾部斜率如何变化？用行为反馈解释概念。
2. 加入不同执行价间距、较高费用和新的预算，而非只增加同形状关卡。测试概念能否迁移。
3. 记录本次操作序列，实现撤销/重做、前后曲线比较与关键选择回放。
4. 增加未限定策略名称的多解题，并允许比较几个满足同一条件的结构。
5. 增加只奖励识别不可能任务的关卡：预算、最大损失和最低收益可能相互冲突。

## 波动率捕手的技术准备

先明确交易语义：持仓、现金、手续费、市场时钟、成交价和结算。首版固定一期限和一组期权，只允许现货对冲。市场路径用可复现随机种子，教学路径和挑战路径分开。

每步按现金流水和完整持仓重估记账；Greeks 分解仅用于解释，不能代替账本。保留无法被近似解释的残差。比较不对冲、固定时间对冲和 Delta 阈值对冲，用相同种子与费用规则评估。

必须包含同起点同终点不同路径、IV 下降和跳跃场景。不要把“实现波动率高于隐含波动率”设成必胜规则。先完整实现一个路径的回放与守恒测试，再扩充六关。

## 专业开发流程

**需求定义**：一个迭代只确定一个学习目标、可观察行为、模型边界、验收条件和反例。

**设计评审**：用可操作的任务原型评审；检查信息量是否过多、玩家是否理解计价单位、失败是否提供可行动反馈。

**经济模型评审**：独立检查公式、账本、边界、费用、保证金口径与极端场景。未来进入专业培训或真实行情用途前，需邀请相关领域专家复核。

**实现**：引擎、关卡、UI 分离；业务逻辑使用纯函数；版本化规则和记录。新增依赖时先说明解决的具体问题。

**验证**：单元检查覆盖经济不变量和反例；浏览器覆盖完整主路径、失败路径、移动端和恢复。不为每个静态文案写镜像测试。

**发布**：同一提交完成检查、归档与部署；保存版本号；失败时使用此前已通过版本回滚。上线功能与未来计划明确区分。

**观察**：小样本访谈优先于先建分析平台。未来收集事件时，先定义每个事件回答的问题，说明保存范围并给用户选择。

## 建议观察指标

当前没有埋点，以下尚未采集：首次添加耗时、首次完成耗时、检验失败原因、提示依赖、独立完成率、变体题成功率、复盘解释质量和再次挑战意愿。

把“完成率高”与“教学有效”分开。若大多数人依赖示范通关，优先改善概念反馈，而不是继续增加奖励。若玩家理解却操作费力，优先改交互。
